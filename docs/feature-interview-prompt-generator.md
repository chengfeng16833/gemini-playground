# 功能设计：对话式访谈 → 提示词编译 → 生成文章

> 状态：设计草案 v1
> 适用项目：gemini-playground（Gemini → OpenAI 格式代理 + 多模态聊天前端）
> 一句话定位：用户给出**模糊需求**，AI 像资深编辑一样**多轮"拷问式"追问**把需求逼清楚，最后把整段对话**自动编译成一份结构化提示词**，再喂给生成模型产出文章/小说。

---

## 1. 背景与价值

### 1.1 要解决的痛点
当前所有 AI 写作工具最大的门槛是**用户不会写提示词**。现有产品多为"引导式填表"（Sudowrite Story Engine、AI_NovelGenerator 设定工坊），但**填表 ≠ 对话**——表单是死的，用户不知道该填什么；而"拷问式对话"是活的，AI 会根据上一轮回答动态追问，体验上更接近"跟一个资深编辑聊天"。

经市场调研，目前**没有一个把"对话采集 → 编译提示词 → 写小说"端到端打通的明星产品/开源项目**，这正是本功能的差异化空间。

### 1.2 与现有机制的关系
本功能的核心机制来源于 Matt Pocock 的 **grill-me** skill（"relentlessly interview the user until reaching shared understanding, resolving each branch of the decision tree. For each question, provide your recommended answer. Ask one at a time."）。

但 grill-me **只负责"逼问清楚"，本身不含"编译成产物"步骤**。本功能在它基础上补齐两段：
- **停止判定**：借鉴学术基准 ReqElicitBench 的"覆盖率 → finish"思路；
- **编译产物**：借鉴 Sudowrite Story Engine 的"结构化中间产物（Story Bible）"+ Anthropic Prompt Generator/Improver 的元提示工程技巧。

## 2. 总体流程

```
[0] 用户输入模糊需求
        "我想写个修仙文"
            │
            ▼
┌──────────────────────────────────────────────┐
│ [1] 意图识别 & 槽位初始化                       │
│   - 从首句提取已知槽位（题材=修仙）             │
│   - 标记未知槽位 → 生成待问队列                 │
└──────────────────────────────────────────────┘
            │
            ▼
┌──────────────────────────────────────────────┐
│ [2] 多轮拷问（循环）                            │
│   每轮：选 1 个最关键缺口 → 问 1 个问题         │
│         + 给 2~4 个候选 + 1 个推荐默认答案      │
│   用户回答 → 回填槽位 → 重算覆盖率              │
│   覆盖率达阈值 或 触顶轮次 → 退出循环           │
└──────────────────────────────────────────────┘
            │
            ▼
┌──────────────────────────────────────────────┐
│ [3] 结构化中间产物（Story Bible / JSON）        │
│   - 把对话沉淀成可编辑的结构化对象              │
│   - 向用户复述确认（"我将据此写…，确认吗？"）   │
│   - 用户可逐条改/删/补                          │
└──────────────────────────────────────────────┘
            │
            ▼
┌──────────────────────────────────────────────┐
│ [4] 提示词编译 + 生成                           │
│   - 结构化对象 → 填入 XML 提示词骨架            │
│   - 自动加 CoT / few-shot / 输出格式约束        │
│   - 调用 /v1/chat/completions 生成正文          │
│   - （可选）正文中发现的新设定回流到 [2]/[3]    │
└──────────────────────────────────────────────┘
```

## 3. 模块详细设计

### 3.1 模块一：意图识别 & 槽位表

定义一张**小说必备槽位表（Slot Schema）**——这是整个功能的"骨架"，决定了 AI 该问什么、何时算问够了。

| 槽位 | 含义 | 是否必填 | 示例取值 |
|---|---|---|---|
| `genre` | 题材/类型 | ✅ | 修仙 / 都市 / 言情 / 科幻 / 悬疑 |
| `length` | 篇幅 | ✅ | 短篇(<1万) / 中篇 / 长篇连载 / 指定章节数 |
| `tone` | 基调氛围 | ✅ | 热血爽文 / 治愈 / 暗黑 / 诙谐 |
| `protagonist` | 主角设定 | ✅ | 身份、性格、动机 |
| `core_conflict` | 核心冲突 | ✅ | 主角要什么、被什么阻挡 |
| `setting` | 世界观/背景 | ✅ | 时代、地点、特殊规则 |
| `gimmick` | 金手指/特色设定 | 网文✅ | 系统流 / 重生 / 签到 |
| `pov` | 视角人称 | ⬜ | 第一人称 / 第三人称限知 |
| `style_ref` | 文风参考 | ⬜ | 模仿某作家 / 某作品风格 |
| `supporting_cast` | 主要配角/反派 | ⬜ | 师父、对手、感情线对象 |
| `plot_outline` | 剧情走向 | ⬜ | 起承转合关键节点 |
| `ending` | 结局倾向 | ⬜ | HE / BE / 开放式 |
| `audience` | 目标读者/平台 | ⬜ | 番茄 / 起点 / 海外英文 |
| `taboo` | 禁忌/避免项 | ⬜ | 避免血腥、避免某类情节 |

> **必填槽位填满率**是停止判定的主要依据；可选槽位用于提升质量但不阻塞。

### 3.2 模块二：多轮拷问

**核心交互原则（来自 grill-me）：**
1. **一次只问一个问题**（one at a time），不要一次抛一堆。
2. **每个问题都附 2~4 个候选 + 一个"推荐默认答案"**。用户一句"就按推荐的来"即可跳过，大幅降低疲劳、也省 token（一轮返工成本 > 一次集中访谈）。
3. **决策树式下钻**：先问高层（题材/基调/篇幅），再依据回答动态展开子问题（选了"修仙"才追问"金手指类型"）。

**追问策略（混合式）：**
- 必填槽位走**固定兜底队列**（保证完整性）；
- 细节追问交给 LLM **动态判断缺口**（保证灵活）；
- 用**追问质量 rubric**（参考 CMU 14 条标准）约束："非冗余、可回答、能推进信息"，过滤废话问题。

**停止条件（双保险，参考 ReqElicitBench）：**
- 主信号：必填槽位填满率 ≥ 阈值（如 100% 必填 + ≥50% 可选）→ 触发 `finish`；
- 兜底：达到最大轮次上限（如 8~10 轮）强制收尾——需求工程文献明确警告"轮数过多体验差"。

**前端实现建议：** 复用类似 `AskUserQuestion` 的选项卡 UI（候选项点选 + "其他"自由输入），而非纯文本框，对模糊型/非技术用户最友好。

### 3.3 模块三：结构化中间产物

**关键决策：对话不要直接拼成自由文本，而是先沉淀成一个结构化 JSON 对象。**（Sudowrite Story Bible 模式）

```json
{
  "genre": "修仙",
  "length": "长篇连载，先写前 3 章",
  "tone": "热血爽文",
  "protagonist": {
    "name": "（待定/AI建议）",
    "identity": "宗门外门弟子",
    "motivation": "为母复仇、登顶大道",
    "personality": "隐忍、腹黑"
  },
  "gimmick": "签到系统",
  "core_conflict": "被同门陷害跌落悬崖，绝境中觉醒金手指",
  "setting": "九州大陆，灵气复苏",
  "pov": "第三人称限知",
  "style_ref": "参考《凡人修仙传》的冷静叙事",
  "ending": "HE",
  "taboo": ["避免小白文套路", "不写无脑后宫"]
}
```

**这样做的三个好处：**
1. **可编辑/可拒绝**——向用户复述时支持逐条改/删/补，用户始终掌控；
2. **可回溯**——编译出的提示词出问题时能定位到是哪个槽位；
3. **可回流**——生成正文后发现的新设定（新角色、新地名）可结构化追加，反哺后续章节一致性。

**收尾确认（参考 LLMREI"总结关键点" + grill-me"确认可以开始了吗"）：**
> "我将据此为你写一篇**热血修仙长篇的前 3 章**：主角是隐忍腹黑的外门弟子、靠签到系统逆袭、第三人称冷静叙事、HE 结局，避免小白套路。**确认开始吗？**（也可以点任意一条修改）"

### 3.4 模块四：提示词编译 + 生成

把结构化对象填入**固定 XML 骨架**，并套用 Anthropic Prompt Generator/Improver 已验证的技巧（CoT 段、few-shot、输出格式约束/prefill）。

**编译出的最终提示词（示意骨架）：**
```xml
<role>你是一位擅长中文网络小说的资深作家，文风冷静克制，节奏明快。</role>

<task>根据以下设定，创作小说正文的第 1 章（约 2500 字）。</task>

<story_bible>
  <genre>修仙</genre>
  <tone>热血爽文</tone>
  <protagonist>隐忍腹黑的宗门外门弟子，为母复仇</protagonist>
  <gimmick>签到系统：每日签到获得资源/功法</gimmick>
  <core_conflict>被同门陷害跌落悬崖，绝境觉醒金手指</core_conflict>
  <pov>第三人称限知</pov>
  <ending_direction>HE</ending_direction>
</story_bible>

<constraints>
  - 第三人称限知视角，全程只跟随主角
  - 避免小白文套路与无脑后宫
  - 开篇即冲突，3 段内进入主角绝境
  - 章末留一个钩子
</constraints>

<thinking>先在心里规划本章的起承转合与情绪曲线，再开始写。</thinking>

<output_format>直接输出小说正文，不要解释、不要标题外的元信息。</output_format>
```

**与 gemini-playground 的对接：** 见第 4 节——直接复用项目已有的 `/v1/chat/completions`（OpenAI 格式）接口调用 Gemini 生成。

## 4. 与 gemini-playground 的集成方案

本项目已具备的能力，**正好能撑起这个功能，几乎不用动后端**：

| 已有能力 | 如何复用 |
|---|---|
| `src/api_proxy/worker.mjs`：Gemini → OpenAI 格式代理 | 访谈追问、提示词编译、正文生成**全部走同一个 `/v1/chat/completions`** |
| 纯前端 `src/static/`（vanilla JS） | 新增一个"小说创作"页面/模块，不引入框架 |
| Deno / Cloudflare Worker 无服务器部署 | 新功能继承同样的部署方式，零额外基建 |

**改动范围（MVP）：**
```
src/static/
├── novel.html                 # 新增：访谈+创作页面
└── js/
    └── novel/
        ├── slot-schema.js      # 槽位表定义（第 3.1 节）
        ├── interviewer.js      # 模块二：追问循环 + 停止判定
        ├── story-bible.js      # 模块三：结构化对象 + 编辑/确认 UI
        ├── compiler.js         # 模块四：JSON → XML 提示词骨架
        └── api-client.js       # 封装对 /v1/chat/completions 的调用
```

**三处 LLM 调用，各用一段系统提示词（system prompt）：**
1. **访谈官 prompt**（驱动模块二）：内置 grill-me 那段指令 + 槽位表 + "一次一问、附推荐答案、输出 JSON 标注当前槽位状态与是否 finish"。
2. **复述确认 prompt**（模块三收尾）：把 Story Bible JSON 转成自然语言复述。
3. **正文生成 prompt**（模块四）：即编译出的 XML 骨架。

> 提示：让"访谈官"每轮**额外返回一个机器可读的状态块**（如 JSON：`{filled_slots, next_question, options, recommended, finish:false}`），前端据此渲染选项卡并判断是否停止——这是把 LLM 对话变成可控状态机的关键。

## 5. 分期落地建议（MVP → 增强）

**MVP（先证明体验跑得通）：**
- 固定槽位表 + 一次一问 + 推荐默认答案
- 简单停止条件（必填填满 or 触顶轮次）
- Story Bible 复述确认（先只读，不支持逐条编辑）
- 编译 XML 骨架 → 生成第 1 章

**V2（提质 & 控制力）：**
- Story Bible 逐条可编辑/拒绝
- 追问质量 rubric 过滤废话问题
- 多章连续生成 + 新设定回流（一致性）
- 编译出的提示词对用户可见可改（信任感 + 老手友好）

**V3（差异化）：**
- 覆盖率驱动的智能停止（向 ReqElicitBench 思路靠）
- 语音/逐步输入采集（自传类产品验证过对非技术用户友好）
- 文风参考样本注入 few-shot

## 6. 关键风险与开放问题

| 风险/问题 | 说明 | 缓解 |
|---|---|---|
| 追问太多惹烦用户 | 文献明确警告轮数过多体验差 | 推荐默认答案 + 硬性轮次上限 + 随时"够了，开始写" |
| LLM 不肯停 / 一直问 | grill-me 的停止是概念性的、无硬算法 | 用槽位覆盖率 + 轮次上限做**程序化**兜底 |
| 编译出的 prompt 质量不稳定 | 自由文本拼接易丢信息 | 强制走结构化 JSON → 固定 XML 骨架 |
| 长篇一致性 | 多章后角色/设定漂移 | 新设定回流 Story Bible；后续可叠加向量检索（见小说工具调研报告） |
| 中文网文"爽点/节奏" | 通用模型常抓不住 | 在生成 prompt 里显式约束节奏（开篇即冲突、章末留钩子） |

**待你拍板的开放问题：**
1. 首发形态是**独立"小说创作"页面**，还是嵌进现有聊天界面的一个模式？
2. 槽位表先按**通用小说**做，还是直接按**中文网文**（强调金手指/爽点/平台）定制？
3. 编译出的提示词**默认是否对用户可见可编辑**？

## 7. 附录：访谈官系统提示词（草稿）

```
你是一位资深小说编辑，正在帮用户把一个模糊的写作想法逼问清楚。

规则：
1. 一次只问一个问题。每个问题给出 2~4 个候选答案，并明确标出你"推荐"的那个。
2. 沿决策树下钻：先确定高层设定（题材/基调/篇幅），再依据回答展开细节。
3. 问题必须非冗余、可回答、能推进信息；不要问已经明确的内容。
4. 当下列必填槽位全部填满时，停止提问，输出 finish。

必填槽位：题材、篇幅、基调、主角、核心冲突、世界观背景。
可选槽位：金手指、视角、文风参考、配角反派、剧情走向、结局、目标平台、禁忌。

每轮回复都附带一个 JSON 状态块（供程序读取）：
{
  "filled_slots": { ... 已确认的槽位 ... },
  "next_question": "下一个问题的自然语言",
  "options": ["候选1", "候选2", "候选3"],
  "recommended": "候选2",
  "finish": false
}
当 finish 为 true 时，filled_slots 即为完整的 Story Bible。
```
